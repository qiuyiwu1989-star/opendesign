# 为什么 AI 做出来的界面都长一样

*(中文发布稿 —— 用于即刻 / V2EX / 少数派 / 公众号。V2EX 建议发在「分享创造」节点)*

---

让 Claude、Cursor、v0 或者 Lovable 给你做个落地页。你其实已经知道会拿到什么了:

- Inter 字体
- 蓝到紫的渐变主视觉
- 满屏 `rounded-2xl`
- 每张卡片下面一层柔和阴影
- 三个并排的功能卡,配 lucide 图标

换个模型试试,一样。下个月再试,还是一样。

这事儿通常被一句「AI 味儿」带过去了。但我觉得这个说法掩盖了真正在发生的事——它不是模型偷懒,也不是你 prompt 写得不好。**这是算术。**

## 平均值没有品牌

一个在几亿网页上训练过的模型,学到的是网页设计的**分布**。当你说「做个现代 SaaS 落地页」而不给别的约束时,概率最高的输出,大致就是这个分布的**质心**。

质心是真实存在的,它确实代表了「大部分页面长什么样」。但也正因如此,**它天然不可能是任何人的品牌**——品牌恰恰是某个团队刻意选择、并长期坚持的那个「偏离平均值的部分」。

所以默认输出同时是:(a) 统计意义上正确的,(b) 商业意义上无用的。所有 AI 做的产品都长得像别的 AI 产品,也就意味着没有一个长得像它自己。

## 为什么 prompt 解决不了

常见的三种尝试:

**「做得高级点 / 极简点 / 可信点」。** 这些是标签,不是指令。模型会把「高级」映射回同一个分布,返回给你**「平均的高级页面」**。你只是把质心缩小了,没有逃出来。

**丢一张截图。** 好一些,至少有真实信号了。但视觉模型看截图给你的是**印象**:「深色背景、无衬线、留白大」。印象不可执行。那个黑到底是 `#08090A` 还是 `#0A0A0A`?正文 15px 还是 16px?大标题的行高具体多少?模型会非常自信地给你一组看起来合理的数字——而它们恰好错在会让设计显得「像盗版」的那个精度上。

**「用 Linear 的设计系统」。** 模型**见过** Linear。但它没有 Linear 的数值,它有的是对数值的记忆。对颜色的记忆,是一个「接近的颜色」。而盗版感就是由一堆「接近」堆出来的。

三种失败方式的共同点:**我们在让模型回忆,而它本该去读取。**

## 真正有效的做法

在生成的那一刻,把一个真实设计系统的**实测数值**交给 Agent。

思路就这一句,实现相当朴素:

1. 用 Playwright 驱动真实浏览器打开真实站点
2. 遍历 DOM,对每个元素读 `getComputedStyle`
3. 按频次聚合——覆盖 40% 表面积的那个背景色就是背景色;覆盖 90% 文本节点的那 5 个字号就是字阶
4. 视觉模型**只负责解释**:命名这套美学、写出「不做什么」——而实测数字是它不能推翻的 ground truth

第 4 步是大部分人会做反的地方。**如果让模型产出数字,你就又回到了「回忆」。模型应该解释测量结果,而不是发明它们。**

每个站输出一份 11 层规范:身份、色彩、字体、间距、表面、布局、组件、交互、动效、语气,以及我认为最重要的一层——**反面清单**(这个设计刻意拒绝做什么)。

```jsonc
// GET https://opendesign.cc/packs/linear/spec.json
{
  "colors": {
    "bg": "#08090A", "ink": "#F7F8F8", "muted": "#62666D",
    "line": "rgba(255,255,255,0.08)",
    "principle": "极端对比制造聚焦,用细微噪点和半透明层次做深度。"
  },
  "typography": { "display": "grotesque-sans", "scale": [ /* 字号/行高/字重/字距 */ ] },
  "spacing": { "base": 4, "scale": [4, 8, 16, 24, 32, 48, 64, 96] },
  "motion": { /* 时长分档 + 缓动曲线 */ }
}
```

不是「Linear 那种深色」,是 Linear 实际在用的那些值。

## 被低估的是「反面清单」

绝大多数设计文档在描述一套系统**做了什么**。但真正有信息量的是它**不做什么**。

Linear 不用弹跳动效。Aesop 首屏不会出现第三种字号。Stripe Press 什么都不加阴影。**这些约束才是让它们各自可辨认的东西**——而它们恰好是「靠记忆重建」时最先被违反的,因为平均页面就是有弹跳动效和阴影的。

给 Agent 一份明确的「这样做会破坏这套品味」清单,纠偏效果比任何正面描述都强。

## 送到 Agent 干活的地方

对我自己来说静态文件就够了,但现实中的 Agent 活在 URL 白名单、沙箱和 CORS 后面。所以这个库开了三层口子:

- **纯 HTTP** —— `catalog.json`、`packs/<slug>/spec.json`、`llms.txt`。不需要 JS,不需要认证
- **协议文件** —— `GET https://opendesign.cc/skill.md` 给 Agent 一套设计总监的工作流:诊断需求、给出立场、路由到参照、拆解成 tokens
- **MCP** —— 7 个工具,远程端点(什么都不用装)或零依赖本地 Node server

```json
{ "mcpServers": { "opendesign": { "url": "https://opendesign.cc/mcp/http" } } }
```

工具设计上有两个决定我想单独说一下:

**`recommend_references` 返回的三个推荐,来自故意不同的美学家族。** 不是相关度 top 3——相关度 top 3 会给你同一个想法的三个变体,等于没给你选择。安全 / 大胆 / 意外,才逼出一次真实的判断。而且家族多样性是**在代码里强制**的,因为在 prompt 里写「记得多样化」不构成任何保证。

**`search_designs` 会告诉你哪些查询词一个都没命中。** 这条来自一个真实 bug:搜 "japanese minimal aesthetic",它曾经非常自信地返回一堆法国极简工作室——"japanese" 零命中,而没有任何东西提示这件事。Agent 无法自行察觉这种失败,它会把结果当答案讲给用户。**静默的部分失败比报错更糟**,所以现在响应里会明确列出没命中的词。

## 还没解决的部分

说点实在的,这些才是有意思的地方:

**检索还是关键词打分,不是语义。** "trustworthy(可信)" 这个词根本不会出现在设计元数据里,按字面匹配几乎没有意义。正确做法是构建期算好离线 embedding。还没做。

**美学家族目前是手写的 tag 规则。** 够用来强制多样性,但诚实的做法是**从 tokens 本身算出家族**——对比度、色相数量、字阶跨度、圆角、动效时长。这些数据已经躺在每份 spec 里了。用实测属性聚类而不是人写的标签,是这个数据集独有的可能性,也是下一件真正要做的事。

**tokens 完整度参差不齐。** 有些条目是一整套系统,有些只有两个颜色和一个字体类别。Agent 现在在 fetch 之前无法分辨。catalog 里应该有个 `spec_completeness` 字段。

如果你的 AI 工作流里「让它好看点」这一步现在每次都产出同一个页面——我觉得缺的就是这一层。也很想知道它在你那儿会从哪里崩。
