# 经验沉淀 · 2026-08 全面体检复盘

> 三路并行代码审查 + 数据实测,发现并修复 30+ 项问题后的教训提炼。
> 每条都是这个项目真实踩过的坑,写下来是为了别的项目不再踩。

---

## 做得好的(值得保持的决策)

1. **Agent-native 三层接入**(纯 HTTP 静态 / skill.md 协议 / MCP 双传输)。同类产品还在做"给人看的网站"时,这里已经把 Agent 当第一公民。先发卡位是真实的。
2. **零依赖架构**。无框架前端 + 无依赖 Node MCP + 标准库 Python 管线——迁移服务器时整个栈拎起来就走,一台 4 核小机器扛 1,400+ 站全量服务。依赖越少,腐烂越慢。
3. **Grounded tokens 理念**(Principle #0:真实值,不是记忆近似)。这是整个产品最正确的一步棋,差异化全部由此而来。
4. **管线全自动化 + 人在环设计**。发现→评估→收录→质检→发布全链路,人只在预算和策展决策点介入。$150 换 1,486 个结构化设计系统,边际成本 ~$0.10/站。
5. **幂等 + 断点续跑的习惯**。ingest 的 per-site 状态机让批量任务中断后可以无损续跑——这轮 20 多小时的批处理跨了多次会话中断,零数据丢失。

## 做得不好的(每条附可迁移的教训)

### 1. 视角盲区:同一个根因踩了三次
境外图床国内不可达(卡图空白)→ Playwright CDN 国内限速 → **健康探活从国内服务器发出,一个月内误杀 368 个活站**(zapier/zed 都被标"死亡")。
**教训:任何"可达性判断"都要先问:从哪儿探测的?探测点的网络位置就是结论的偏见。** 强死亡信号(DNS 不解析)和弱信号(连接超时)必须区分对待。

### 2. 自动化即自动破坏的风险
自动探活=自动误杀;自动排名=差点一次性归档整个库;自动评估=配置错了每天白烧 50 次调用且日志看起来"正常"。
**教训:每个自动化必须有 (a)单轮幅度上限 (b)可回滚(软删除而非硬删除) (c)心跳里"跳过"和"崩溃"可区分。** 自动化的失败模式默认是静默的,要主动设计"这坏了我怎么知道"。

### 3. 多写者无互斥
4 个 cron 各自 flock 自己的锁,互相之间零互斥,03:00/04:00 的全库脚本和每 10 分钟的 job runner 必然撞车,慢者覆盖快者。
**教训:锁保护的是数据,不是脚本。共享同一份数据的所有写者必须共享同一把锁。** 写盘用 tmp+rename 原子替换。

### 4. 会漂移的常数必然漂移
站点数量在 6 个文件里手写了 4 套口径(500+/545+/900+/实际 1486);schema 落后实现 4 个字段;文档说 AND 实现是 OR;线上 skill.md 和仓库版是两个不同文件。
**教训:同一事实只允许一个来源。数字动态注入,schema 变更与代码变更同 commit,"文档即代码"不是口号是纪律。**

### 5. LLM 输出的格式漂移枚举不完
mimo 的花样:camelCase token、weight 1000、null 字段、翻译时把 JSON 键名也翻成中文(layout 里混进"骨架"键)、错字键(analogogy/borners)。逐个打补丁修了四轮,每轮都以为修完了。
**教训:对 LLM 结构化输出,用 schema 白名单剪枝(prune),不要用黑名单修补(patch)。** 白名单一次写对,永远兜得住新花样。

### 6. 快速开发攒下的安全债要专门还
RLS `using(true)` 的 DELETE(一条 curl 清空全站收藏)、远程数据裸进 innerHTML、DB 字段拼 shell 命令、常驻服务被 4 字节打挂——没有一个是"高级"漏洞,全是默认值没收紧。
**教训:公开产品上线前,必须有一轮"攻击者视角"的对抗审查,和功能开发分开做。** 转义函数写了不等于用了(escapeHtml 躺在文件里,主渲染路径一处没用)。

### 7. 缓存要区分对象
30 天 immutable 缓存打在 404 上(用户把"图不存在"记一个月);常驻进程内存缓存永不过期(MCP 一直 serve 上线瞬间的快照);SW 的 stale-while-revalidate 让用户每次发版拿旧 JS。
**教训:缓存策略必须区分 成功/失败、短命进程/常驻进程、内容会变/不变。** 失败绝不能长缓存;常驻进程的内存缓存必须有 TTL。

### 8. 检索质量的地基是数据卫生,不是算法
检索差的三个原因按影响排序:①summary 用错字段(套话占一半)②tag 词表分裂(30 组重复变体)③无未命中反馈(查询词没命中就静默给错误结果)。全修完之前,任何"更聪明的算法"都是白搭。
**教训:检索优化先做数据审计——字段有没有信号、词表干不干净、失败模式诚不诚实——再谈算法。**

### 9. 库存资产要有"是什么"的第一性认知
探活误杀的深层原因:把"外链可达"当成条目价值。实际上库的资产是已抽取的设计系统档案(在自己 COS 上),原站挂了档案反而更珍贵(Wayback Machine 逻辑)。认知错了,自动化就朝错误的方向优化。
**教训:先回答"我们的资产到底是什么",再设计自动化的取舍规则。**
